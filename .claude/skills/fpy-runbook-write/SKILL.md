# 发票云运营操作指引编写规范

根据原始业务材料、交接清单、飞书文档、系统截图或口头描述，编写面向销售、伙伴、交付与运营经办人的操作指引。结合本地已有文章保持术语和流程衔接一致。

## 核心设计原则

1. **规则与步骤合一**：操作前写清必要的准入条件与业务红线，在相关步骤旁补充具体限制。共用规则可引用统一规则页，同时保留执行本流程必需的摘要。不为追求一页篇幅删掉关键细节。
2. **一线业务语言**：避免程序代码、数据库内部字段和系统设计术语；界面真实显示的字段名、按钮名、报错原文及操作必需的业务编号应准确保留。
3. **事实有据，缺失明示**：菜单、权限、天数、金额、适用范围、审批人、自动动作、完成条件和异常处理均须有材料支持。缺失信息用 `【待确认：具体问题】` 标记，不用常识或其他流程补齐。
4. **区分适用范围**：不得将一个渠道、版本或部署方式的流程直接推广到其他范围。只有材料证明一致时才共用步骤；标题和正文明确本文覆盖的范围。

### 业务术语与背景

以下用于识别术语，不是穷尽的系统名单，不能据此推断具体菜单、权限或流程；具体操作以本文适用范围内的原始材料为准。

- **KBC系统**：商务提单、直分销下单、线索报备。
- **云之家**：智能审批流程。
- **EOP系统**：租户管理、授权下发、通道配置、用量监控、特批延期。
- **租户平台**：客户自助查询开票量、税号权益。
- **票省事小程序**：移动端售后咨询、售前预约、产品报价。
- **UTR（使用到续约）和 LTC（商机到回款）**：业务阶段或管理体系，不是系统工具。
- **标准版**：SaaS轻量化产品；**AI星瀚**：原旗舰版；**AI套件**：原星空旗舰版，与金蝶云·星空基础平台及 ERP 账套关联。名称映射、产品边界和部署支持须结合材料核实。

正文使用统一产品名称；实际界面仍使用旧名称时保留界面原文，说明名称对应关系。背景信息与新材料不一致时列出冲突，不静默覆盖。

## 写前材料覆盖度评估

先确定谁在什么范围内完成什么操作，再检查材料能否支持执行。单篇文章默认内部检查；批量整理时展示评估表，单篇有关键缺失或冲突时简要说明。

| 检查维度 | 核查内容 |
|---|---|
| 适用范围 | 渠道、产品版本、部署方式、办理场景 |
| 前置条件 | 经办角色、权限、所需材料 |
| 业务规则 | 期限、额度、审批条件及例外，按实际流程检查 |
| 操作过程 | 系统入口、菜单路径、操作顺序、关键字段 |
| 流程分支 | 各渠道、版本、部署方式的差异及分支条件 |
| 完成与衔接 | 如何验证成功，是否还有后续人工或系统操作 |
| 异常处理 | 材料中已有的退回、报错及升级处理方式 |

按实际适用的渠道、版本或场景分别判断，不按栏目填满比例评分：

- **材料足够**：关键规则和操作链路有依据，可形成可执行稿。
- **部分缺失**：主体流程明确，先写有依据的部分，列出缺失及是否影响执行。缺少非必要的异常示例，不必阻断成稿。
- **关键材料缺失**：缺少决定性规则、关键步骤或完成判断，只整理已有事实和补充清单；如输出文档，明确标为“草稿：关键材料待补充”，不能宣称可直接执行。

“不适用”与“没有材料”必须区分：只有材料支持时才能判断无需审批、没有后续流转等。材料缺失不能写成无需办理。

### 来源与冲突处理

- 读取相关原始材料；已有文章用于比对和衔接，不能自动视为最新事实。
- 记录关键规则和步骤对应的来源：文档链接、本地路径及章节、截图名称或用户本次说明。能获取时记录版本或更新时间，不编造日期。
- 用户明确说明是最新规则或纠正旧知识时，采用其明确适用的范围，在交付说明中记录变更依据；其他来源冲突要核对时间、渠道、版本和场景，无法消解则列为待确认。
- 材料齐全不代表事实无冲突，文案核对不代表已验证线上系统。
- 不因材料不足清空已有文章；改写时保留有依据且仍适用的细节，对不确定内容明确标注。

## 图片与系统截图改写规范（图文转化法则）

当原始材料中包含系统截图、画板或飞书导出的图片占位符时：

1. **先确认能否读取原图**：图片占位符和 alt 文字不能替代原图。优先查看可访问的原图；仅有 OCR 时可提取清晰明确的文字，但标明未核对原图。看不清、被裁切或无法访问的关键内容列为待确认，说明需要哪部分材料。
2. **转为操作说明**：不机械照抄“画面上方有红色箭头”等冗长 OCR 描述。将能确认的操作提炼为路径和步骤，例如 `模块名 → 二级菜单 → 【目标按钮】`。截图只显示局部入口时，不补造上级菜单；红框不能单独证明操作顺序或审批规则。
3. **界面字段表格化**：复杂表单可整理为字段表，包含字段名、填报说明、是否必填、已显示的选项或来源中的示例。只填写材料能确认的信息；截图中的示例值不等于固定值，已显示选项不等于完整选项集，不能仅凭空白字段推断是否必填。
4. **文字优先，保留必要视觉信息**：材料足够时，读者应能仅凭文字和表格完成操作。若图形位置、复杂配置或识别特征仍依赖图片，保留必要图片及文字说明；关键内容无法读清时，不承诺已完全文字化。
5. **精炼图注**：保留本地图片时按目标文档位置计算相对路径，使用简短客观的图注；截图中的个人信息、账号或客户数据不直接当作填报示例。

   ```markdown
   ![功能界面名称](图片相对路径.png)
   *图 X：[简短说明，20字以内]*
   ```

## 输出文档模板（默认五段式）

以下占位内容仅说明结构，不代表实际业务规则；写作时按材料替换或删除，正文不保留模板提示和设计解释。

默认使用五段式内容安排。为兼容当前本地 `wiki-lint`，保留 `## 适用场景`、`## 操作步骤` 的准确名称，步骤 H3 使用 `第X步：`。其他章节按实际需要调整：无审批的流程使用“业务规则”等名称，不强行插入审批。无需额外操作时不拆造步骤满足数量要求；旧校验器仍要求至少两步时，在交付说明中报告冲突。

```markdown
---

channel: 通用
---
```

### 格式、内链与来源

- frontmatter 使用上述五个字段；`channel` 只填 `金蝶中国渠道`、`发票云自营渠道`、`通用` 中的一个值，与当前本地校验规范一致，不把备选项整行写入。
- `description` 不超过50字且不重复标题。`updated` 填本次实际更新日期，不代表业务规则生效日期；规则生效日期有来源时另在正文说明。
- YAML 字符串包含冒号等特殊字符时正确引用。H1 与 `title` 保持一致。
- 不给所有文章附加三大版本或所有部署方式，只列有依据覆盖的范围。多个分支需明确分支条件，避免读者串用。
- 文章及图片链接均以目标 Markdown 文件所在目录计算，路径使用 `/`；含空格等字符时使用有效的 Markdown 链接写法。检查目标存在，不复制固定的 `../../` 前缀。
- 业务对接优先引用库内 `0 导航与速查/0.2 运营对接人与系统入口速查.md`，相对路径按保存位置计算；后续指引不存在时标 `【待补充链接：文章名称】`，不生成假链接。
- 来源支持读者理解或核对关键规则时，在相应位置保留链接；其余来源映射放在交付说明中，不塞入 frontmatter 或暴露无关客户信息。

## 工作执行流与交付

1. **明确范围与输出方式**：根据请求确定文章范围及位置。只要求草拟时在对话中输出；要求保存或改写文件时按指定位置执行。先查阅相关现有文章，避免无意重复建文。
2. **核查材料与图片**：按实际渠道、版本、部署方式评估覆盖度，提取来源，核对截图可读性，识别关键缺失和冲突。无需每次先让用户确认表格；能独立完成的部分继续处理，只对影响正确性且无法推定的问题请求补充。
3. **组织正文**：使用默认骨架，前置规则放在操作前，按真实流程展开步骤；保留必要的字段说明、示例、限制和异常处理，区分自动动作与人工动作。
4. **交付前自检**：逐步对照来源，检查范围与分支、步骤完整性、图片推断边界、完成条件，再检查 frontmatter、标题、内链和图片路径。仅报告实际完成的检查；自检不能代替业务确认或线上验证。
5. **交付正文与简短说明**：说明输出位置或文件路径、材料状态（足够／部分缺失／关键缺失）、主要来源、待确认项及其是否影响执行。已有写入授权时不再为同一写入重复请求确认；业务事实未确认时保持草稿状态。后续使用旧 Agent 或 lint 时，本 Skill 负责操作指引写作，旧规范的 explainer 模板不在此范围内；遇到规则冲突报告具体差异，不通过虚构业务内容消除校验问题。
